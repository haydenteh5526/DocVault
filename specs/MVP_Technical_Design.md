# MVP technical design

**Design draft, 10 November 2026.** The revised 6 November proposal and feasibility study define the project scope. The first epic is for one household document owner to take an electricity bill from upload to reviewed facts, an exact split among four housemates and one approved internal reminder. Demo 1 demonstrates the review step. The end-to-end proof of concept is targeted for 18 December 2026.

Use the [ticket index](Tickets.md) for delivery order and the [repository snapshot](Repo_Current_State.md) for verified behaviour and limits.

## What the owner can ask

| Example request | Intended behaviour | Current evidence |
| --- | --- | --- |
| “How much is this bill, and when is it due?” | Identify the owner's bill and return the facts with source passages. Ask which bill if several match. | The detail screen shows read-only candidates and OCR lines. In chat, the confirmed values and their source lines are shown in a card; verified by tests, a browser scenario and a manual check on a disposable stack (issue #5). |
| “Split it equally between the four of us.” | Resolve the confirmed bill and ordered housemate labels, then call the calculator. | The split API and panel are merged (issue #2). In chat the assistant shows an unsaved preview from the calculator and asks which people when a name is not a saved housemate (issue #5, tests and a manual check). |
| “Remind me two days before it's due.” | Calculate the proposed reminder date, show the exact change and request approval before saving. | In chat the assistant creates a pending proposal and links to the bill, where the owner approves it (issue #3 approval route). Verified by tests, a browser scenario and a manual check (issue #5). |
| “Draft a question about this charge.” | Compose editable enquiry text using the charge and its evidence. The owner decides what to do with the draft. | In chat the assistant returns a template filled with the confirmed values and up to three matching bill lines, in an editable box with a copy button; nothing is sent (issue #5, tests, a browser scenario and a manual check). |

Personalisation comes from the authenticated owner's documents, reviewed facts and choices in the conversation. If a request is unsupported, explain the boundary and offer a supported next step. Payments, external sending and autonomous browsing are outside the agreed workflow.

## Architecture and evidence flow

React uploads the PDF or image to FastAPI. The API stores the original in private S3-compatible storage and queues processing in Redis. The ARQ worker runs local Tesseract OCR and stores the transcript in PostgreSQL. Opening the owner-scoped document detail derives candidates for the amount, billing period and due date. Each candidate retains its labelled source line, including conflicting lines when found. Since the dashboard redesign (issue #48, PR 2) this review covers any utility bill (broadband, water, gas, phone or electricity): text with the word bill, invoice or statement and at least one labelled amount, due-date or billing-period line, on documents typed `Bill`, `Insurance`, `Contract` or not yet classified. A signed preview lets the owner compare the original file. This read-only review is implemented on the Demo 1 branch. [Rehearsal and evidence](../evaluation/demo-1/README.md)

Owner confirmation is implemented in [PR #13](https://github.com/haydenteh5526/DocVault/pull/13). Confirming appends a `bill_revisions` row with the amount in integer cents, the due date, the billing-period endpoints and a snapshot of the reviewed evidence; earlier revisions are never changed. Each save is bound to the evidence and revision number the owner had when editing started. The server checks both under a row lock on the document and otherwise answers 409 with a reason code and saves nothing. The client then reloads the document before the owner tries again, and an unsaved correction survives switching tabs. Its API, component and browser tests pass in CI, and an API test shows a save waiting for an uncommitted transcript edit.

The equal split was merged in [PR #16](https://github.com/haydenteh5526/DocVault/pull/16) (`d21d018`); issue #2 was closed on 12 November 2026 after the manual check with the synthetic PDF. The owner's housemate labels live in a `housemates` table, and a split names them by id, so the server only splits among labels it finds in the caller's account. A preview writes nothing. A save appends a `bill_splits` row holding the confirmed revision it used, the rule, the total and a snapshot of the labels and cents. It is bound to the revision number, the latest split number and the shares the owner reviewed, checked under the same document row lock, and otherwise answers 409 with a reason code and saves nothing. A split from an older revision is returned as stale, with its own amount and revision, and is never recalculated. In the browser, cached data is dropped when the account changes and the service worker stores no API responses. Four housemates is the acceptance case, and the calculator and API accept 2 to 12.

Reminder proposal and approval were merged in PR 21 as `3ec5918` on 16 November 2026, and issue #3 is closed. A request carries only the allowlisted action `bill_reminder`, a number of days and the revision, split and proposal numbers the owner had on screen; unknown fields are refused. The server builds the amount, due date, reminder date and shares from the owner's confirmed revision and current non-stale split, and stores them as an immutable pending `reminder_proposals` row with a `proposed` event. Approval sends back the details the owner reviewed and is bound to them, to the stored revision and to the split. Under the document row lock it saves a `reminders` row (unique on the proposal) and records `approved` and `saved`. If the inputs changed, that transaction marks the proposal stale with the reason, records it, saves nothing and answers 409. The first approval answers 201, and any repeat answers 200 with the same outcome. A cancelled or stale proposal cannot be approved, and a saved one cannot be cancelled. The reminder is a record in the owner's account only, and a reminder date that has passed is allowed and labelled in the panel. The newest saved reminder stays on screen when a later proposal is cancelled or goes out of date.

Chat requests (issue #5, server merged in PR 22, web cards on `feature/issue-5-assistant-chat`) pass through one selection. A selector returns a tool name from a fixed list with typed arguments: a local Ollama model when `ASSISTANT_MODEL` is set (empty by default), otherwise, or when the model times out or returns anything invalid, a deterministic keyword router. The selector sees only the owner's message, the owner's earlier messages, a one-line server-written summary of each earlier assistant turn, the titles of the owner's bills (at most 10 of the 50 newest documents) and the owner's housemate names. It never sees document text or earlier assistant prose. The server then resolves the bill and the people against the caller's own records (a reference that is not one of the caller's bills, or a name that is not a saved housemate, becomes a question and is never guessed), runs `latest_revision`, `preview_split` or `propose_reminder`, and writes the reply itself from their results. Model-written prose appears only in answers to general document questions, through the existing retrieval answer. Nothing is approved or saved as a split or reminder from chat: a split is only previewed, a reminder is only a pending proposal with `source="assistant"`, an enquiry draft is a template that is shown and not stored, and payments and sending are declined with the available alternative when the selector recognises the request (the keyword router misses some paraphrases, which then get a general answer; see the limits in [Repo_Current_State.md](Repo_Current_State.md)). A missing input is stored as a question with the request it belongs to, and the next message fills it or is treated as a new request.

## Design for the next increments

| Story | Data and responsibilities | Acceptance evidence |
| --- | --- | --- |
| [#1 · Confirm bill facts](https://github.com/haydenteh5526/DocVault/issues/1) | Keep OCR evidence separate from owner corrections. On explicit confirmation, FastAPI validates ownership and saves a revision with EUR cents, billing-period endpoints, due date, document reference and a snapshot of the reviewed evidence. Later edits produce a new revision. | Reopen a correction with its source. Reject another owner's access. An unclear date requires a decision. |
| [#2 · Allocate shares](https://github.com/haydenteh5526/DocVault/issues/2) | A pure server calculator accepts a confirmed revision and an ordered list of labels. For the first equal split, divide integer cents by the number of labels and give one extra cent to each of the first remainder labels. The UI shows the rule and total. | €123.47 splits into €30.87, €30.87, €30.87 and €30.86. Test exact division, empty labels and a changed bill revision. |
| [#3 · Approve a reminder](https://github.com/haydenteh5526/DocVault/issues/3) | Store an owner-scoped pending proposal containing the bill revision and exact reminder details. Approval identifies that proposal. In one transaction, verify it is pending, still current and owned by the caller, save the reminder and record the outcome. Enforce uniqueness on the proposal-to-reminder link. | Cancellation or stale inputs produce no reminder. Concurrent or repeated approval returns the same saved outcome. Verify history and failed ownership checks. |
| [#5 · Ask in natural language](https://github.com/haydenteh5526/DocVault/issues/5) | The selector (a keyword router by default; a local model was evaluated and none passed) may select a retrieval, calculation, enquiry-draft or reminder-proposal tool. FastAPI supplies the authenticated identity and validates typed arguments. Approval is a separate owner interaction. OCR text and retrieved passages are evidence only. | Exercise paraphrases, ambiguous requests, unsupported tools, a malicious instruction in a bill and an unanswerable question. Record model, configuration, citations and outcomes. |

The proposed reminder states are **pending**, **cancelled**, **stale** and **saved**. A change to the confirmed bill revision or reminder details requires a new proposal and fresh approval. A retry of an already saved proposal returns its recorded reminder. Housemate labels exist within the owner's account.

## Constraints on planned writes

- The server derives identity from the session and checks ownership of the source document, confirmed revision, proposal and saved record. The model may suggest tool arguments. The server validates them against the owner's records and available operations.
- Preserve the original OCR evidence and record corrections as a new confirmed revision. Missing or conflicting candidates require inspection and explicit confirmation before downstream work can use them.
- Store amounts and calculate contributions in integer cents. The four contributions must sum to the confirmed total. The order of the labels used for remainder cents must be visible in the split.
- Approval binds the owner to one proposal and one confirmed bill revision. Cancellation, an ownership failure or a changed revision leaves the reminder unsaved. Record the outcome alongside the proposed and approved details.
